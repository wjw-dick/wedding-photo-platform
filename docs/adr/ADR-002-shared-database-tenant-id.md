# ADR-002：共享库 + tenant_id 多租户隔离

- 状态：已接受
- 日期：2026-11
- 决策人：技术负责人、DBA、安全评审

## 背景

租户数预期 ≤ 50，单租户约 5 万会员、8 万订单，客片 8 TB 存放在对象存储而非数据库。需要低成本开通（≤ 3 分钟）、跨租户汇总、统一升级；同时必须满足跨租户 403 的硬性验收。

## 决策

采用共享库 + 全表 `tenant_id` + 复合索引；MyBatis-Plus 租户拦截器自动注入 `tenant_id`；Service 层按 ID 查询显式带租户条件；平台表使用 `platform_` 前缀并被拦截器排除。Redis 使用 `tenant:{id}:*`，对象存储使用 `tenants/{id}/`，MQ 消息携带 `tenantId`。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A 共享库 + tenant_id（采用） | 开通快、成本低、跨租户报表简单 | 依赖拦截器正确性，存在漏加风险 | 采用 |
| B 独立 schema | 隔离更强、备份独立 | 50 套 DDL 版本管理、连接池与迁移复杂 | 不采用 |
| C 独立数据库 | 最强隔离 | 开通与运维成本高，汇总需额外数仓 | 不采用 |

## 后果

- 正面：新租户初始化仅插入默认角色/菜单/参数/门店，3 分钟内可用；平台可实时汇总。
- 负面：最大风险是漏加 `tenant_id`；共享资源可能相互影响。
- 缓解：
  - 拦截器 + 显式条件双保险；
  - 越权用例纳入回归（A 租户 token 访问 B 租户订单/会员/客片）；
  - CI 静态扫描新增表是否含 `tenant_id` 与复合索引；
  - 预留 `TenantDataSource` 抽象，租户 > 50 或单租户 > 500 万行时评估升级独立 schema。
